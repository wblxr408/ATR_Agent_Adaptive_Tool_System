## 发现

### R1 · P1 · JSON 键名中的已知秘密不会脱敏

位置：`atr/storage.py:42`、`atr/storage.py:189`。

`Redactor.data` 对字典值脱敏，却原样保留 `str(k)`。有效 JSON Artifact 又直接序列化此结果，不再对整个文档执行已知秘密替换。因此只要输出将配置为秘密的字符串放进键名，保存的 Artifact 与分页读取就会包含该秘密。例如已知秘密为 `example-key-value`，输出对象 `{"example-key-value":"ok"}` 的键会原样保存，即使摘要的文本脱敏已经将其遮盖。

这影响计划第18/21项的凭证与统一脱敏要求。应同时处理键和值，并明确键脱敏后重名的处理方式。后续验证需要覆盖已知秘密作为键名、嵌套键名以及摘要/完整 Artifact 的一致性。

### R2 · P1 · 工作区扫描误用交付文件的128文件上限

位置：`atr/service.py:286`、`atr/runtime/sandbox.py:221`、`atr/runtime/sandbox.py:236`。

根写调用用 `_collect(execution_workspace, max_workspace_bytes)` 收集工作区基线；沙盒及最终提交也调用同一收集器。该函数除了字节预算，还硬编码 `len(result) >= 128`。因此过滤后的项目只要有129个普通文件，即使总量远低于64 MiB，写调用和写入 Review 也会在执行前返回 `artifact_limit`。恰好128文件的项目新增第129个文件也会在提交检查时失败。

这会阻止普通规模的 Coding 项目，不能用交付 Artifact 的文件数量限制代替工作区策略。应给两种收集用途使用明确的独立限制及错误码。后续验证应覆盖129个小文件的现有项目，以及从128文件新增一个文件的正常修改。

### R3 · P1 · 固定旧版本失败会回退无关的当前健康版本

位置：`atr/service.py:366`、`atr/service.py:377`；`atr/control/registry.py:315`。

任何固定版本的运行发生输出契约错误，都会寻找更旧版本并调用全局 `registry.rollback`，没有核对当前活跃指针是否仍指向失败版本。例如活跃版本是健康的 v3，显式调用固定 v2 时失败，代码会隔离 v2，并把全局活跃版本改成 v1，覆盖本来无关的 v3。并发升级时同样存在这一问题。

这破坏计划第16项的版本选择边界。隔离失败版本可以独立执行，但修改活跃指针应在同一事务中校验其仍等于失败版本；针对该次运行的旧版建议应与全局选择分开。现有回退用例只覆盖“失败版恰为当前活跃版本”。

### R4 · P1 · 关闭服务时排队调用仍可能执行副作用

位置：`atr/service.py:83`、`atr/service.py:183`、`atr/service.py:195`。

`close()` 只给 `cancel_flags` 中已有的运行设置取消标记；标记是在 `_run` 开始时才注册的。线程池中已接收但尚未开始的任务没有该标记。随后 `executor.shutdown(wait=True)` 默认继续执行排队任务，且 `_run` 不检查关闭状态，因此它们可在服务关闭过程中继续执行已授权的工作区或外部写入，而非收到取消。

这与运行说明中的退出取消语义不一致。应在关闭时阻止新接收、持久标记本实例所有未完成任务取消，并取消尚未开始的 Future，确保运行状态及幂等记录也结束。后续验证应覆盖单工作线程、一个活动调用、一个排队写调用以及关闭后写效果仍为零。

### R5 · P2 · 模型结果包异常会丢失已经取得的用量

位置：`atr/adapters.py:160`、`atr/adapters.py:169`、`atr/service.py:461`。

模型代理先解析 `usage` 并构造 Cost，随后才访问 `choices[0].message.content`。若供应商结果包含有效 usage/账单标识，但 choices 缺失、为空或结构错误，函数在返回 AdapterResponse 前退出；已构造的费用没有传给 Ledger。运行时仅记录未知费用并保留上界。`choices=[]` 还会抛出当前异常列表未捕获的 IndexError，最终表现为 `internal_error`。

预算预留仍然存在，所以不能把它描述为费用被当作免费；实际问题是已知 Token 和账单标识丢失，错误分类也不稳定。应分开保存供应商使用量与验证结果正文，即使正文/包结构失败也保留已知费用证据。

### R6 · P2 · null 根输出会跳过 expected_path 检查

位置：`atr/service.py:647`、`atr/service.py:649`、`atr/service.py:655`。

Review 仅在 `actual is not None` 时检查非空 expected_path。程序成功输出 JSON `null`，用例设置 `expected=null`、`expected_path="required_field"` 时，路径检查被跳过，`found` 保持 True，随后比较 `None == None` 使 Review 通过。配合允许 null 的输出契约，缺失路径并不会被结构验证拦住。

这让不存在的字段也能成为通过准入的证据。应在 expected_path 非空时始终解析路径，并用独立的“路径未找到”状态区分合法 null。已有“缺失字段且期望 null”用例的根输出是对象，没有覆盖根输出为 null 的分支。
